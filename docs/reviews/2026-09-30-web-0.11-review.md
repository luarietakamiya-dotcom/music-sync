# MusicSync Web v0.11.0 レビュー

> この文書は v0.11.0 時点の発見と比較を記録したものです。R1〜R4 と R6 は
> v0.11.1 で修正し、R5 は事前容量表示と実際の上限の説明を追加しました。
> 96 MiB の合成バス上限そのものは残ります。修正の検証結果は
> [Validation record](../validation.md) を参照してください。

確認日: 2026-09-30。レビュー対象: 現在のソース、ビルド済みWeb、Core公開API。

## 結論

Web版は、ブラウザ内の解析・適応仕上げ・音量一致A/Bと、再利用可能なCoreの基盤ができている。
一方、Desktopの自動ミックスに対しては、STEM読み込みと合成を追加した段階である。
素材別の自動音量調整・補正・マスキング対策は未実装であり、機能同等ではない。

新しいDSPを増やす前に、入力時のデータ保持とSTEM登録を修正すべき。
今回、ブラウザで3種類の不具合（うち単体A/Bの破損入力を別々に確認）、
Coreで1件の安全方針の不一致を再現した。容量案内・レポートの説明にも修正が必要。
音質の優劣を試聴評価した結論ではない。

## 比較根拠と確認範囲

- ユーザー指定の **impact.64 Creative Mode Hub** 配布物内の変更履歴を再確認。
  演出の排他的選択、通常音質への復帰、複数のレトロ・空間モードを明記している。
- 回収済みソースの `app.py` は **impact.67**。`native_core/stem_session.py`、
  `io.py`、`final_guard.py` を参照。impact.64と完全一致するソースではない。
- Desktop実行ファイルは今回起動していない。Desktop欄は資料・実装の存在を示す。
  現在のWindows GUIでの正常動作や、両者の数値・音質同等性は主張しない。
- Webはユーザーの既存タブと別の一時的なChromiumで境界条件を確認。
  合成テスト音源だけを使用し、ユーザーの曲や現在のA/Bには触れていない。
- アプリのコード修正は実施せず、レビュー資料と再現用プローブを作成した。

既存調査: [Desktop構成](../current-architecture.md)、[以前の比較](../desktop-web-gap-analysis.md)。

## 先に修正する点

### R1 / P1: 単体ファイルの読み込み失敗で既存A/Bが失われる

**再現:** A/Bがある状態で破損した `bad.wav` をAへ読み込むと、A/B両方の選択が無効になる。
Bへ読み込んだ場合も、元のBが消える。元ファイルをディスクから削除する問題ではなく、
アプリ内の未保存の音声・候補・設定文脈が失われる問題。

**原因:** `apps/web/src/main.ts:264–297`。`loadFile()`はデコード前に`begin()`を呼び、
そこで既存の`source`、比較計画、仕上げレポート、A変更時にはSTEM一覧も消す。
後段で失敗しても戻せない。STEM一括取り込みだけは成功時に置き換える設計になっている。

**改善:** A/B共通で「検証・読み込み・解析成功後に入れ替える」処理に統一する。
失敗・キャンセルでは音声だけでなくレポート、素材一覧、選択状態も保持する。
メモリ不足なら現在の作業を消さず、その入力を断る。

**確認条件:** 破損WAV、失敗FLAC、上限超過、Worker起動失敗、キャンセルの各ケースで
既存A/BのPCM・レポートが保持され、次の正常入力だけが置き換わる。

### R2 / P1: ボーカル＋伴奏の誤判定を画面で修正できない

**再現:** ペアモードで `vocals.wav` と `no_vocals.wav` を追加すると、両方が`vocal`になり失敗。
「役割を設定してください」と表示されるが、素材一覧は0件で修正する欄がない。
`Vocal Removed.wav`、`ボーカルなし.wav`も同様にボーカルと判定される。

**原因:** `packages/core/src/stems.ts:15–18`は否定表現より先に`vocal`等へ一致する。
`apps/web/src/main.ts:339–400`は、合成成功前の新規ファイルを編集可能な一覧へ登録しない。
ファイル名判定を改善するだけでは、未知の名前・役割の誤認識全般を解決できない。

**改善:** まずファイルを待機一覧へ登録し、役割を直してから合成できる状態を必ず残す。
ペアモードには「ボーカル」「伴奏」の2つの投入先を用意し、ファイル名は補助情報とする。
`no_vocals`等の否定表現は優先して扱う。役割の選択だけで音声を理解したと表示しない。

**確認条件:** 否定表現、両方不明、両方同役割、日本語名、逆順追加でも
再ドロップやファイル名変更を強制せず、画面の役割変更で完成できる。

### R3 / P1: 処理中に続けてSTEMを追加すると素材が抜ける

**再現:** 2素材を登録後、3つ目の読み込み中に4つ目をドロップすると、
結果は1・2・4の3素材になった。3つ目が欠落したのに成功と表示される。
Worker起動待ちを遅延させ、同じ操作順を確実に再現した。

**原因:** `apps/web/src/main.ts:338–363,408–410`。追加は確定済みの`stemEntries`から
毎回作られ、処理中の候補を引き継がない。次のドロップが先行Workerを終了させる。
fieldsetの無効化では、dropイベントによる呼び出しは防げない。

**改善:** 受け付けたファイルを独立したプロジェクト待機列に追加し、処理要求は直列化する。
別案として処理中のドロップを明示的に断ることは可能だが、「1つずつ追加」の体験には
待機列の方が適する。表示は登録済み・処理待ち・処理済みを区別する。

**確認条件:** 連続ドロップ、FLAC待ち、解析中追加、キャンセル直後の追加で
受け付けた素材が欠落・重複せず、画面の素材数と実際の合成数が一致する。

### R4 / P2: STEMの安全方針がWebとCoreで異なる

**再現:** ハードクリップした素材と伴奏を`mixStems()`で合成し、資料どおり
`autoMixMaster(mixed.audio)`へ渡した。元素材のクリップ数は **12,000**、
合成後のクリップ数は **0**、最終結果は **accepted**、理由は空配列だった。
合算後の減衰でサンプル値が下がっても、元のクリッピングは修復されていない。

**原因:** 元STEMのクリップを理由に自動採用を保留する規則は
`apps/web/src/main.ts:507–508`にだけ存在する。`auto/engine.ts:38–42`は
渡されたPCMだけを見るため、合成前の品質情報を知らない。
CoreのPCM API自体から元のクリップ履歴を復元することはできない。

**改善:** `finishStemProject`等のCore統合入口を設け、素材ごとの品質情報と
ミックス計画を最後の評価まで運ぶ。Webも外部アプリも同じ規則を利用する。
汎用PCM APIの責務は明記し、公式のSTEM利用例を統合APIへ切り替える。

**確認条件:** 同一STEM入力に対してWebと外部Core利用の採否・警告が一致する。
除外した素材のクリップは採否に影響せず、使用中素材の履歴は合算減衰で消えない。

### R5 / P2: 「各100 MiB / 10分」と実用上限の関係が分かりにくい

**確認:** `apps/web/index.html:26`の案内に対し、
`STEM_LIMITS.maxBusBytes`と自動仕上げの入力上限は96 MiB。
ステレオFloat32の合成バスだけで計算すると、48 kHzでは **262.144秒（約4分22秒）**、
96 kHzでは約2分11秒まで。48 kHz・5分の2素材は、メタデータ検証で拒否された。
さらに素材合計384 MiB等の制約もあるため、最大16素材・10分を同時に利用できる意味ではない。

**改善:** 読み込み前に、その素材数・レート・チャンネル数で扱える長さを分かる形で表示する。
上限を数値だけ大きくするのではなく、バッファの寿命・再解析回数・チャンク処理を見直す。
普通の1曲を途中で分割せず完了できることを長期の性能目標にする。

**確認条件:** 容量予測と実際の採否が一致する。長尺や多素材で、処理時間・ピークメモリ・
キャンセル応答を実測する。短い合成音だけのテストを長尺性能の証拠にしない。

### R6 / P2: レポートのファイル名について説明が古い

**確認:** `SECURITY.md:17`には「JSON exports omit filenames」とあるが、
STEMの仕上げレポートには`sourceMix.plan.tracks[].name`および素材レポートの名前が入る。
`main.ts:548,623–626`でそのままJSONへ保存する。自動送信はなく、ローカル書き出しの内容と
説明の不一致である。

**改善:** 公開・不具合報告向けの匿名化レポートを用意し、素材名ありの詳細版と区別する。
匿名化は名前だけでなく、名前を含む将来の説明・エラー欄にも適用する。
SECURITYと利用案内を現在の実装へ更新する。

**確認条件:** 匿名化版に素材名・パスが残らず、素材間の対応は匿名IDで追える。

## 製品思想に合わせた改善順

### 1. 入力を安心して使える状態にする

R1〜R4を最優先に修正し、R5・R6の案内も合わせる。
`main.ts`に混在する「素材登録」「確定A/B」「進行中ジョブ」「失敗した候補のレポート」を
別の状態モデルに分ける。表示中の設定と実際に聴いている候補の設定を明確にし、
未適用の設定を変えたら「まだ音には反映されていません」と一貫して表示する。

### 2. ボーカル＋伴奏で本当の自動ミックスを作る

素材別Analysis → StemMixPlan → 素材別DSP → Bus Analysis → Mastering → Quality Gate。
最初は2素材に絞り、「声が小さい」「声が伴奏に埋もれる」場合の控えめなレベル調整と
帯域整理を実装する。各素材を同じLUFSへ無条件にそろえる方式にはしない。
既に良いバランスなら何もしない。

「ボーカルの存在感」はVocal STEMがあれば声の素材へ、完成曲1本なら全体への
限定的な音色調整へ分岐する。通常画面は「声を前へ／伴奏となじませる」などの意図で操作し、
dB・閾値はAdvancedに置く。素材Soloで誤登録と位置ずれを確認できるようにする。
役割変更が実際の計画へ反映されたこともレポートで確認可能にする。

### 3. 1曲を完成して持ち出せるようにする

セッションの保存・復帰、候補履歴、素材再リンク、出力形式の選択を整える。
現状の「原音へ戻す」はB解除であり、前のSTEMバランスや前候補に戻る多段Undoではない。
処理不要の良好な素材や、ユーザーが警告を理解した未処理ミックスも保存できる経路を検討する。
ラウドネス用途、実測値、達成可否、形式をExport前にまとめて表示する。

### 4. 測定と実曲で仕上がりを検証する

ブラウザの推定値を「良い音の保証」として扱わない。権利を確認した実曲で
音量一致・可能ならブラインド比較を行い、ジャンル別・既にマスター済み・静かな曲・
分離STEMの残留成分・強い歪み・逆相・冒頭末尾の無音等を評価する。
長尺完走の時間・メモリ、モバイル、全体アプリのSafari/Firefoxも別途検証する。
リファレンス追従や専用修復は、この基盤の後に追加する。
